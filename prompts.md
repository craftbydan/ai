# handwriting-ai — prompt pack

## Prompt 1: Project setup and tooling

### Context
Empty folder containing only `CLAUDE.md`, `prompts.md` and `.env.example`. This prompt creates the whole skeleton so every later prompt can run build, type-check, lint and tests. Nothing here depends on a GPU.

### Goal
A monorepo with a FastAPI backend and a Next.js frontend that start with one command, pass type-check, lint and tests, and talk to each other through a health check. A tiny set of synthetic test fixtures exists for later prompts.

### Needs from you
Nothing.

### Use these (pinned)
- FastAPI + uvicorn, SQLAlchemy 2, Alembic, pydantic-settings, pytest, httpx, ruff, mypy: latest stable at install time. Record exact versions in CLAUDE.md under "Resolved versions".
- Next.js (App Router) + TypeScript strict + Tailwind CSS + vitest + eslint + @playwright/test: latest stable at install time.
- Pillow, numpy, opencv-python-headless, pypdfium2, reportlab, pikepdf.
- An OFL handwriting font for fixtures and the fake renderer: Caveat, from https://github.com/google/fonts/tree/main/ofl/caveat . If the network blocks the download, use any OFL-licensed handwriting-style font already on the machine and note which in CLAUDE.md. Save the licence text next to the font.

### Build
1. `git init` if needed. Add `.gitignore` (data/, .env, .env.local, node_modules, .venv, .next, __pycache__, vendor/, weights).
2. Create the folder structure from CLAUDE.md (empty packages with `__init__.py` are fine).
3. `services/api/pyproject.toml` with the dependencies above, extras `dev` (pytest, httpx, ruff, mypy) and `ml` (torch, transformers; do NOT install `ml` in this prompt). `src/hwai/config.py` reads every env var in `.env.example` with safe defaults (`RENDERER=fake`, `OCR=fake`).
4. `src/hwai/main.py` app factory with CORS for `WEB_BASE_URL`, `GET /health` returning `{"status":"ok","renderer":"fake","ocr":"fake"}`, and the standard error shape from CLAUDE.md (a handler turning unhandled exceptions into `{"error":{"code":"internal","message":"..."}}` with status 500).
5. Alembic initialised against SQLite at `DATA_DIR/hwai.sqlite`; an empty initial migration; `make migrate` works.
6. `apps/web`: Next.js app with a home page that calls `GET /health` through `src/lib/api.ts` and shows "API: ok" or a readable error.
7. `Makefile` with every target listed under Commands in CLAUDE.md. `make dev` starts both servers.
8. Fixtures in `services/api/tests/fixtures/`: the font, plus `make_fixtures.py` that generates (a) `hand_page_1.png` — a 1240x1754 page of 12 known sentences drawn with the font with random baseline wobble, saved with a `hand_page_1.json` of the exact text per line; (b) `card.pdf` — a 5x7 inch blank card with a printed border and a "To: ____" line; (c) `planner.pdf` — a page with 10 ruled lines and 2 empty boxes; (d) `blank.png`. Generation is deterministic (fixed seed).
9. Tests: pytest for `/health` and for config defaults; pytest that fixtures exist and the JSON line count matches; vitest for `api.ts` error handling with a mocked fetch.
10. Fill in "Resolved versions" in CLAUDE.md.

### Do NOT
- Do not implement any handwriting, OCR, agent or auth logic.
- Do not install torch or transformers.
- Do not add a UI library beyond Tailwind.

## Prompt 3: Renderer interface, fake renderer, jitter and export

### Context
Depends on Prompt 1 (font, fixtures) and Prompt 2 (storage). No GPU model yet. This prompt defines the `Renderer` contract the real model will fill in Prompt 4, plus the natural-variation and export machinery that works with any renderer.

### Goal
Given a word and a style, the system can produce a transparent handwriting image of that word with per-letter-looking variation, and can export a flattened PDF or PNG that is clearly marked as AI generated.

### Needs from you
Nothing.

### Use these (pinned)
- Pillow (+ its FreeType text drawing) with the Caveat font for `FakeRenderer`.
- numpy for jitter maths; `reportlab` and `pikepdf` for PDF output; Pillow PNG text chunks.

### Build
1. `render/base.py`: `StyleRef`, `WordImage`, abstract `Renderer` with `render_word(...)` exactly as in CLAUDE.md. `render/__init__.py` has `get_renderer()` choosing by `RENDERER`.
2. `render/fake.py`: draws the word in the font on a transparent canvas, tracks baseline offset, and uses the `seed` to vary size (±4%), rotation (±2°), baseline wobble and ink colour darkness so the same word with different seeds differs.
3. `render/jitter.py`: pure functions `apply_jitter(img, seed, strength)` (small affine wobble, stroke-width variation via morphology, slight ink opacity noise). Deterministic for a seed.
4. `text/splitter.py`: `TextSplitter` interface and `EnglishSplitter` (words and punctuation as separate units, newlines preserved).
5. `export.py`: `export_png(page_image, overlay_layers) -> bytes` and `export_pdf(pages, size_points) -> bytes`. Both add AI-generated marking: PDF metadata (`Keywords: AI-generated`, `Subject: Generated with handwriting-ai`), a PNG text chunk `ai_generated=true`, and a small grey footer mark "AI generated" drawn bottom-right at 7 pt equivalent. Coordinate conversion pixels→points lives only here.
6. Tests: same word + same seed → identical bytes; same word + different seeds → different bytes; output has alpha channel and non-empty bounding box; PNG export contains the `ai_generated` chunk; PDF export metadata contains `AI-generated`; the footer mark region is non-blank in the exported image.

### Do NOT
- Do not import torch or One-DM.
- Do not lay out text on pages (Prompt 7).
- Do not let any export skip the AI-generated marking, and do not add an option to turn it off.

### Acceptance criteria
- `get_renderer().render_word("hello", [], seed=1, size_px=64)` returns an RGBA image whose non-transparent bounding box is wider than 40 px.
- Two calls with seeds 1 and 2 produce different pixels; two calls with seed 1 produce identical pixels.
- `export_pdf` output opened with pikepdf has `Keywords` containing `AI-generated`.
- `export_png` output read with Pillow has `info["ai_generated"] == "true"`.
- Rendering an empty string returns a 1x1 transparent image and does not raise.
- All checks in `make test`, `make typecheck`, `make lint` pass.

### Verify
1. `make test` → passes, including the 6 tests in Build.
2. `python -m hwai.render.fake --demo "Dear Dan, thank you!" --out /tmp/demo.png` (add this small CLI) → writes a PNG; open it and see the sentence with visibly different letter shapes between runs with different `--seed`.
3. `python -c "import pikepdf; print(pikepdf.open('/tmp/demo.pdf').docinfo)"` after `python -m hwai.export --demo` → shows the AI-generated keyword.

### Leaves behind
- `Renderer` contract, `FakeRenderer`, `get_renderer()`, `apply_jitter`.
- `EnglishSplitter`, `export_png`, `export_pdf` with mandatory AI marking.
- CLI demos `python -m hwai.render.fake` and `python -m hwai.export`.

## Prompt 4: One-DM renderer and cost measurement

### Context
Depends on Prompt 3 (`Renderer` contract and fake). This is the first prompt that needs a GPU. Everything else in the pack keeps working with `RENDERER=fake`, so if the GPU is not available this prompt is **blocked** and later prompts continue.

### Goal
`RENDERER=onedm` generates real handwriting word images in the style of a given sample image using One-DM, and a script reports seconds and baht per rendered page.

### Needs from you
- A machine with an NVIDIA GPU and CUDA (rented cloud GPU is fine), with the repo checked out on it.
- `ONEDM_WEIGHTS_PATH`: path to the One-DM English checkpoint (from the One-DM README links).
- `GPU_COST_THB_PER_HOUR`: price per hour of that GPU in THB.

### Use these (pinned)
- One-DM, https://github.com/dailenson/One-DM, MIT code (verified: official ECCV 2024 code, one-shot style from a single word image). Clone into `vendor/One-DM`, pin the commit hash in CLAUDE.md. Follow its README for the real inference entry point; wrap it, do not rewrite it.
- `torch`/`transformers` via `pip install -e ".[ml]"` (`make install-ml`), matching the CUDA version the One-DM README requires.

### Build
1. `make install-ml` target; clone One-DM into `vendor/One-DM` (gitignored), record commit hash and the resolved versions in CLAUDE.md.
2. `render/onedm.py`: class `OneDMRenderer(Renderer)`. Loads the model lazily on first call, keeps it in memory, accepts the `StyleRef` word image as the style sample, resizes and normalises as One-DM expects, runs inference for the word, then converts the greyscale output to a transparent RGBA image (ink = darkness, background removed) and applies `apply_jitter` with the `seed`. If `StyleRef` list is empty, raise a clear error `no_style_ref`.
3. Batch support: `render_words(words, style_refs, seed)` that renders several words in one GPU batch where the model allows it.
4. `scripts/measure_cost.py`: renders 3 pages of ~180 words each using one fixture style crop, times it, and prints seconds per page and `seconds/3600 * GPU_COST_THB_PER_HOUR` per page in THB, plus a warning if above 1.0 THB. It writes `data/cost_report.json`.
5. Tests (run without GPU): the converter from model output array to RGBA is unit-tested with a synthetic array; `get_renderer()` returns `OneDMRenderer` for `RENDERER=onedm` without importing torch until `render_word` is called; empty style refs raise `no_style_ref`. Add a GPU-only test marked `@pytest.mark.gpu`, skipped unless `RUN_GPU_TESTS=1`.

### Do NOT
- Do not change the `Renderer` interface.
- Do not train or fine-tune anything.
- Do not claim the public weights are cleared for paid use; keep the Launch gate note.
- Do not commit weights or the vendored repo.

### Acceptance criteria
- With no GPU, `make test` passes and the GPU test is reported as skipped.
- On the GPU machine with `RUN_GPU_TESTS=1 pytest -m gpu`, rendering "hello" from a fixture crop returns an RGBA image whose bounding box is non-empty.
- Rendering the same word with two different seeds yields different images.
- `python scripts/measure_cost.py` writes `data/cost_report.json` with fields `seconds_per_page`, `thb_per_page`.
- Importing `hwai.render.onedm` does not import torch.

### Verify
1. `make test` (any machine) → passes, GPU test skipped.
2. On the GPU machine: `RENDERER=onedm RUN_GPU_TESTS=1 pytest -m gpu -q` → passes.
3. `RENDERER=onedm python -m hwai.render.fake --demo "hello world" --out /tmp/o.png` (the demo CLI honours `RENDERER`) → image with plausible handwriting.
4. `python scripts/measure_cost.py` → prints the two numbers and writes the JSON file.

### Leaves behind
- `OneDMRenderer` and `render_words` behind `RENDERER=onedm`.
- `make install-ml`, pinned One-DM commit in CLAUDE.md.
- `scripts/measure_cost.py` and `data/cost_report.json` format.

## Prompt 5: Learn the hand (OCR, word cut-outs, style profile)

### Context
Depends on Prompts 2 (uploads, `page_images`, `word_samples`) and 3 (`EnglishSplitter`). Uses `OCR=fake` for tests and `OCR=trocr` for real runs. A style profile is the set of best word crops of the user's own writing, paired with the text they spell, which the renderer uses as style references.

### Goal
After uploading handwriting documents, a background job finds lines, reads each line, cuts out words, scores them, and stores a ready-to-use style profile. More pages produce more samples.

### Needs from you
Nothing. (Real OCR downloads `microsoft/trocr-base-handwritten` from Hugging Face on first use; that needs normal internet access on the machine running `OCR=trocr`.)

### Use these (pinned)
- TrOCR: `microsoft/trocr-base-handwritten` via `transformers` (line-level handwriting OCR), imported lazily inside `TrocrOcr`.
- `opencv-python-headless` for binarisation, line and word segmentation (projection profiles and connected components).
- `FakeOcr` that reads the `hand_page_1.json` ground truth, for tests.

### Build
1. `hand/ocr.py`: `OcrEngine` interface, `FakeOcr`, `TrocrOcr`, and `get_ocr()` by env `OCR`.
2. `hand/segment.py`: pure functions `find_lines(page_img) -> list[BBox]` (deskew lightly, binarise with adaptive threshold, horizontal projection) and `split_words(line_img) -> list[BBox]` (vertical gaps wider than a threshold relative to line height). Return crops with a small padding.
3. `hand/ingest.py`: for each page of a `hand_documents` row: find lines → OCR each line → align OCR words to word boxes by order (if counts differ, keep the line only for single-word-safe cases or drop it) → save crops to `DATA_DIR/<user>/crops/` → insert `word_samples` with `text`, `crop_path`, size, OCR confidence, and `quality_score` (ink contrast, stroke clarity, aspect ratio sanity).
4. `hand/profile.py`: choose up to 150 best samples; ensure variety (not 150 copies of "the"); `style_refs_for(hand_id, k=...) -> list[StyleRef]` picks refs at random with a seed so repeated renders vary. Set `hands.status = ready` when at least 20 usable samples exist, otherwise `failed` with a reason like `not_enough_ink`.
5. Run ingestion as a FastAPI background task, with `GET /hand` showing `status`, `sample_count` and per-document status. Re-uploading more pages adds samples and recomputes the profile.
6. Tests using `FakeOcr` and `hand_page_1.png`: lines found equals the JSON line count (±1); at least 80% of words have a crop; resulting `sample_count >= 20` and `status == ready`; a blank page (`blank.png`) yields status `failed` with `not_enough_ink`; two different seeds in `style_refs_for` give different orderings.

### Do NOT
- Do not train any model on the user's data in this prompt.
- Do not send documents to any external OCR service.
- Do not touch page analysis of target files (Prompt 6).

### Acceptance criteria
- Uploading `hand_page_1.png` (own-hand box ticked) and waiting for the job leaves `GET /hand` with `"status":"ready"` and `sample_count >= 20`.
- Uploading only `blank.png` leaves `"status":"failed"` and a human-readable reason.
- Every `word_samples.crop_path` points to an existing file whose width and height are both above 8 px.
- `hand/segment.py` functions are importable and tested without torch.
- `make test`, `make typecheck`, `make lint` pass including the 5 tests in Build.

### Verify
1. `make test` → passes.
2. With `OCR=fake make dev`: `curl -F file=@services/api/tests/fixtures/hand_page_1.png -F own_hand_confirmed=true localhost:8000/hand/documents`, wait 5 s, `curl localhost:8000/hand` → JSON with `"status":"ready"`.
3. Open three random files from `data/*/crops/` → each shows a single word that matches its `text` in the database (`sqlite3 data/hwai.sqlite "select text,crop_path from word_samples limit 5"`).
4. Optional, with network and `make install-ml`: `OCR=trocr` run of the same upload still reaches `ready`.

### Leaves behind

## Prompt 6: Read the target page (lines, boxes, blank areas)

### Context
Depends on Prompt 2 (chat files, `page_images`) and Prompt 5 (line detection helpers can be reused for ruled-line detection but this prompt works on printed, mostly blank pages). Output is a list of writeable `Region`s per page that the layout engine and the agent use.

### Goal
For any uploaded card, letter template, planner, notebook page or image, the backend returns the page size and a list of regions where text can sit: ruled lines, empty boxes and large blank areas, each with coordinates.

### Needs from you
Nothing.

### Use these (pinned)
- `opencv-python-headless`: Hough/morphology line detection, contour boxes, distance transform for blank-area finding.
- Pillow, numpy. Types `Region` as in CLAUDE.md.

### Build
1. `page/analyze.py`: `analyze_page(img) -> PageAnalysis(width, height, regions, ink_mask_coverage)`.
   - Ruled lines: long thin horizontal strokes → `Region(kind="line", baseline_px=y, line_height_px=gap to next line or a default)`.
   - Boxes: closed rectangular contours that are mostly empty inside → `kind="box"`.
   - Blank areas: largest axis-aligned empty rectangles away from existing ink, with a 3% page margin → `kind="blank"`, at most 4 per page.
2. `page/regions.py`: stable region ids (`p1-line-03`), sorting top-to-bottom, merging fragments of the same ruled line, drop regions smaller than 40 px in either dimension.
3. `POST /chats/{id}/files` now also runs analysis and stores `analysis_json`; add `GET /chats/{id}/files/{file_id}/analysis` returning it, and `GET /chats/{id}/files/{file_id}/pages/{n}.png` returning the page image (ownership checked).
4. A debug overlay function `draw_regions(img, regions)` that draws labelled rectangles, used later by the agent.
5. Tests with the fixtures: `planner.pdf` yields 10 line regions (±1) and 2 box regions; `card.pdf` yields at least 1 blank region covering the card centre and no region overlapping the printed border; `blank.png` yields exactly one blank region; region ids are unique and stable between two runs.

### Do NOT
- Do not call any LLM here; this is classical image analysis.
- Do not render text (Prompt 7).
- Do not handle rotated or photographed pages beyond a simple deskew of up to 5 degrees.

### Acceptance criteria
- Analysing `planner.pdf` returns between 9 and 11 `line` regions and exactly 2 `box` regions.
- Analysing `card.pdf` returns at least one `blank` region whose centre is within 15% of the page centre.
- No returned region extends beyond the page bounds.
- Running analysis twice on the same file returns identical JSON.
- `GET .../analysis` returns the stored JSON; another user gets 404.
- `make test`, `make typecheck`, `make lint` pass including the 5 tests in Build.

### Verify
1. `make test` → passes.
2. Upload `planner.pdf` to a chat (as in Prompt 2) then `curl localhost:8000/chats/<id>/files/<fid>/analysis | python -m json.tool` → shows 10 line regions and 2 box regions.
3. `python -m hwai.page.analyze services/api/tests/fixtures/card.pdf --overlay /tmp/card_overlay.png` (add small CLI) → open the PNG: rectangles sit on empty areas and avoid the border and printed text.

### Leaves behind
- `analyze_page`, `Region` JSON format, `draw_regions`.
- Endpoints for analysis and page images.
- Stored `chat_files.analysis_json`.

## Prompt 7: Layout engine (words placed on regions with natural jitter)

### Context
Depends on Prompt 3 (`Renderer`, `apply_jitter`, `EnglishSplitter`, export), Prompt 5 (`style_refs_for`) and Prompt 6 (`Region`, page images). Works with `RENDERER=fake` for tests and `onedm` in real use.

### Goal
Given a page, a `Placement` (which region, what text, alignment, size, slant, jitter), the engine renders every word in the user's style and composes them onto the page so the result looks hand-written: words wrap inside the region, sit on the baseline, and no two identical words look identical.

### Needs from you
Nothing.

### Use these (pinned)
- Own modules from Prompts 3, 5 and 6. Pillow and numpy only for composition.

### Build
1. `layout/place.py`: `layout_text(region, text, align, size_scale, slant_deg, jitter, seed, renderer, style_refs) -> PlacedText(list[PlacedWord(x,y,image)])` with:
   - font size derived from the region's `line_height_px` (lines) or from the box height (boxes) times `size_scale`;
   - word wrapping inside the region width, centred vertically in boxes and blank areas, line spacing 1.2× size, support for explicit newlines;
   - alignment left, center, right per line;
   - per-word baseline wobble, slight size variation and small rotation drawn from the seed; slant applied as a shear;
   - text that does not fit: shrink size by up to 40% in steps, then return `fit=false` with how many words were cut, never draw outside the region.
2. `layout/place.py::compose(page_img, placed_texts) -> PIL.Image` pastes ink with multiply-style blending so ruled lines show through, and returns the preview image.
3. `Placement` model in `schemas.py` as in CLAUDE.md, validated (text length ≤ 2000 characters, size_scale 0.5–1.5, slant −15 to 15).
4. `POST /chats/{id}/render` with body `{placements: [...]}` → stores a `renders` row (next `version`), writes `preview_path`, returns `{version, preview_url, fit_report}`. `GET /chats/{id}/renders/{version}/preview.png`.
5. `POST /chats/{id}/export?version=N&format=pdf|png` → uses `export.py` (marking mandatory) at the original page size; returns the file.
6. Tests using `FakeRenderer`: text centred in the `card.pdf` blank region has its ink bounding box centre within 5% of the region centre; every ink pixel lies inside the region box; a 3-line text on `planner.pdf` line regions sits on the correct baselines (ink bottoms within 6 px of baselines); too-long text returns `fit=false` and still draws nothing outside the region; same seed twice gives identical previews; different seeds differ; the word "the" repeated 5 times yields 5 distinct word images.

### Do NOT
- Do not call the LLM; placements come from the request body here.
- Do not bypass the AI-generated marking on export.
- Do not write outside region bounds, ever.

### Acceptance criteria
- `POST /chats/{id}/render` with a centred placement on the `card.pdf` blank region returns a preview whose pixels outside the region match the original page exactly.
- The same request with seed 1 twice yields byte-identical previews; with seed 2 it differs.
- A 3,000-character text returns 422 validation error; a 400-character text in a small box returns `fit=false` or a shrunk size, with no ink outside the box.
- Exported PDF has page size equal to the original and `AI-generated` in its metadata.
- `make test`, `make typecheck`, `make lint` pass including the 6 tests in Build.

### Verify
1. `make test` → passes.
